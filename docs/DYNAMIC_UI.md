# Живой интерфейс Shunt: предложение

Статус: предложение, 14 сентября 2026 года. Описанные ниже изменения ещё не реализованы. Основание — текущие `src/web/main.py`, `static/index.html`, `ui.js` и ограничения `design/BRIEF.md`.

## Что именно меняем

Shunt уже получает живые данные: статус опрашивается, скорость и журналы используют SSE, терминал — WebSocket. Статические HTML/CSS/JS определяют способ доставки интерфейса, а не предел его интерактивности. Сохраняем шесть разделов, обе темы и отсутствие сборки. Развиваем обзор, обратную связь и переход от показателя к объяснению.

## 1. Обзор как действующая карта сети — первый приоритет

На десктопе главный блок занимает примерно две трети ширины: «Домашняя сеть → Shunt → Напрямую / Туннель». Справа — активный выход, состояние резерва и время обновления. Под картой — график скорости за последние 60 секунд и события текущего сеанса. На телефоне карта становится вертикальной, затем идут скорость и состояние выхода; подробности открываются по нажатию.

- Узлы отражают подтверждённое состояние: активен, резерв, недоступен, неизвестен. Изменение состояния сопровождается коротким переходом цвета и текстовым пояснением.
- Рядом со шлюзом — входящая и исходящая скорость из `/api/speed-stream`. История за минуту накапливается в браузере с момента открытия; пропуски показываются разрывами.
- На ветвях — доли соединений за выбранный период из `/api/analytics/summary`. Подпись периода обязательна. Эти числа не обозначают текущие соединения, объём или скорость трафика. Для скорости каждой ветви потребуется отдельное измерение на сервере.
- Нажатие на ветвь открывает соединения с соответствующим фильтром. Переход не должен создавать впечатление, что текущий журнал содержит все записи из суточного агрегата: его окно и ограничения показываются отдельно.
- Вместо бесконечно бегущих «пакетов» — спокойное обновление цифр и короткое выделение изменившегося узла. Размеры блоков стабильны, цифры табличные. При сниженной анимации переходы отключаются.

Нужные источники уже есть: `/api/status`, `/api/speed-stream`, `/api/analytics/summary`, `/api/analytics/series`. Новый API для первой версии карты не нужен.

## 2. «Почему этот адрес идёт сюда?» — второй приоритет

Адрес в списке соединений открывает боковую панель шириной около 440 px; на телефоне — панель на весь экран. Вверху назначение и время проверки, ниже три последовательных шага: перехват netfilter, решение ядра, правило xray и выход. Ссылка на соответствующий раздел позволяет изменить правило, сохранив контекст проверки.

Использовать существующий `/api/path/to?target=…`: он возвращает `interception`, `kernel`, `xray`, разрешённые адреса и признак IPv6. Это проверка текущей конфигурации и маршрута к назначению. Нельзя выдавать её за реконструкцию исторического пакета или доказательство успешной доставки. Неизвестный этап показывается прямо, без зелёной галочки. Запрос выполняется при открытии панели или повторной проверке, а не для каждой строки таблицы.

## 3. Найденные блокировки как понятная очередь решений

Вместо одинаковых строк — компактные состояния: «ожидает подтверждения», «направляется в туннель», «исключено». В строке видны последняя проверка, результат напрямую и через туннель, число подтверждений. Детали раскрываются на месте.

Источник — `/api/discovered`: `rows`, `probe`, `schedule`, `last_run`. Порог подтверждений берём из настроек, а не фиксируем числом 2. Если нужного поля нет, показываем отсутствие данных. Кнопки используют существующие операции проверки и включения/исключения записи. Сначала уточняем гранулярность: общую проверку нельзя подписывать как проверку одного адреса, если API запускает весь список.

## 4. Настройки с видимым результатом — вместе с первым этапом

Для профиля, выхода и правил вводим одинаковую последовательность:

**Есть изменения → Применяем → Настройки сохранены → Состояние проверено.**

Черновик формы хранится отдельно от состояния сервера. Фоновый опрос не меняет выбранный сервер и не стирает ввод. На время запроса блокируется только соответствующее действие. Ошибка остаётся рядом с ним, черновик сохраняется; можно повторить запрос.

Успешный POST означает принятие операции, но не обязательно готовность туннеля. После сохранения читаем доступный статус. Если API не позволяет подтвердить конкретную настройку или операция ещё выполняется, явно показываем «сохранено, ожидаем подтверждения» вместо преждевременного «готово». Для длительных операций используем реальные фазы из их status API; проценты не придумываем. Откат предлагаем только там, где он действительно поддержан.

## 5. События выхода — после основных изменений

Рядом с резервом полезна короткая лента: основной выход потерян, включился FPTN, основной восстановлен. В первой версии можно фиксировать наблюдавшиеся переходы `/api/status` в текущем сеансе, с подписью «замечено в …». Время обнаружения браузером не равно времени события на шлюзе.

Для достоверной истории после перезагрузки страницы нужен серверный журнал переходов с временем, предыдущим/новым состоянием и причиной, если она известна. Это отдельная доработка backend. Не восстанавливаем историю догадками из текущего статуса.

## Как реализовать без сборки

Обычные JS-файлы: слой запросов и подписок, состояние данных и черновиков, отдельные функции обновления виджетов. SVG остаётся встроенным, графики — существующие средства или лёгкий SVG. Новые внешние зависимости не требуются.

Для каждого экрана определяем запуск и остановку его запросов. Видимый обзор получает скорость с существующей частотой 1 раз в секунду; статус — с текущим интервалом 5 секунд; суточные агрегаты — 30 секунд. Скрытая вкладка прекращает обновления отображения и ненужные подписки; возврат запрашивает свежий снимок. Тяжёлую диагностику `/api/path` оставляем на её экране, не добавляем в глобальный секундный цикл.

Журнал соединений обновляем пакетами, сохраняя прокрутку и выделение; предусмотрены пауза и ограниченное число отображаемых строк. Начальный ориентир — не чаще 4 обновлений DOM в секунду и не более 500 строк, затем измерение на реальном устройстве. Это целевой бюджет, а не подтверждённая оценка нагрузки.

Отменяем устаревшие запросы и игнорируем поздние ответы предыдущего экрана. Ошибка связи сохраняет последний снимок с отметкой давности; ноль не подставляется вместо ошибки. После потери авторизации обновления прекращаются. Новый общий SSE-эндпоинт рассматриваем только если замеры покажут пользу; перевод всего интерфейса на WebSocket не требуется.

## Порядок внедрения и приёмка

1. Живая карта, свежесть данных и единое применение настроек. Проверить потерю/возврат связи, сохранность черновика при опросе, неизвестный статус и обе темы на 1440×900 и 390×844.
2. Переход от ветви к соединениям, панель объяснения и очередь найденных блокировок. Проверить фильтры, фактические ответы API, IPv6 и отсутствие данных.
3. Серверная история переключений, если нужна история вне текущего сеанса; оптимизация транспорта по результатам измерений.

На каждом этапе: проверить, что навигация не множит подписки, поздний ответ не меняет чужой экран, обновление не сбрасывает фокус, недоступность сервера не выглядит нормальным нулём. Проверки на локальном стенде дополняются измерениями нагрузки и реальных переходов основного/резервного выхода на шлюзе.
